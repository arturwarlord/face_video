# ArturChat — собственная инфраструктура звонков

## Решение

Не использовать коммерческую SIP/IP-телефонию, trial-планы и публичные TURN-реле.
Оставить Android WebRTC-клиент и заменить внешнюю инфраструктуру звонков собственным сервером.

### Компоненты

1. **Сигнализация — Kotlin Ktor + WebSocket.**
   Сервер принимает авторизованные соединения клиентов, маршрутизирует приглашения, SDP offer/answer и ICE-кандидаты между двумя участниками. Ktor поддерживает WebSocket-сессии и двусторонний обмен сообщениями.
2. **Медиареле и NAT traversal — coturn.**
   Свой STUN/TURN сервер. Он используется, когда прямой WebRTC-маршрут между мобильными сетями невозможен. coturn — свободная открытая реализация STUN/TURN; программная лицензия не означает бесплатный хостинг.
3. **Хранилище — PostgreSQL или SQLite на собственном узле.**
   Для MVP достаточно хранить учётные записи, сессии, приглашения и состояние звонков. Впоследствии туда переносится остальная серверная логика.
4. **Android.**
   Сохраняются существующий WebRTC SDK, экран вызова, mute/speaker/end и логика микрофона. Меняется поставщик сигнализации и список ICE-серверов.
5. **Push — отдельный этап.**
   При открытом приложении звонок может поступать через постоянное WebSocket-соединение. Для надёжного пробуждения приложения после закрытия/выгрузки Android обычно нужен системный push-канал. Возможный российский вариант — RuStore Push, но это отдельная зависимость, не собственная инфраструктура. Без push нельзя обещать надёжный входящий звонок при полностью закрытом приложении.

## Что означает «всегда бесплатно»

Бесплатными могут быть исходный код, сборка и лицензии компонентов. Для звонков через интернет всё равно необходим постоянно доступный публичный узел:

- сервер должен быть включён и подключён к интернету круглосуточно;
- необходим доступный извне адрес (публичный IPv4 или корректно работающий IPv6);
- должны быть открыты TCP/UDP порты сигнализации и TURN, включая диапазон relay-портов;
- нужен канал с достаточной пропускной способностью для голосового трафика.

GitHub Actions не заменяет постоянно работающий сервер: runner не является постоянным сетевым узлом. Бесплатный trial VPS также не удовлетворяет требованию «всегда бесплатно».

### Реальные варианты размещения

- **Собственный компьютер/мини-ПК + доступный публичный адрес + настройка роутера.** Нет ежемесячной аренды сервера, но компьютер, интернет и электричество должны оставаться включёнными. При CGNAT или отсутствии доступа к настройкам роутера входящие соединения из мобильных сетей могут быть недоступны.
- **Бесплатный облачный сервер без срока окончания.** Нельзя считать гарантированным вариантом, пока конкретный поставщик письменно не подтверждает постоянный тариф и его ограничения. Trial/промокредиты не подходят.
- **Только прямой P2P без своего relay.** Не требует TURN в успешных сетях, но часть NAT/мобильных сетей не пропустит прямое соединение. Это режим best-effort, а не надёжная телефония.

## Поэтапный переход

### Этап A — подготовить self-hosted voice backend
- Добавить Ktor WebSocket signalling service.
- Добавить конфигурацию coturn с временными учётными данными (TURN REST auth); секреты хранить только на сервере.
- Ограничить сигнализацию участниками конкретного звонка, проверять размер/тип сообщений, TTL приглашений и лимиты соединений.
- Добавить health-check и интеграционные тесты сигнализации.
- Описать Docker Compose для сервера и TURN.

### Этап B — переключить Android-клиент
- Вынести signaling transport за интерфейс, чтобы не переписывать WebRTC/UI.
- Подключить авторизацию к собственному backend.
- Загружать временный ICE-конфиг с собственного backend.
- Не использовать публичные Google/Cloudflare STUN endpoints и Open Relay.
- Оставить Supabase только временно для текущих чатов/авторизации, пока не готов полный перенос; в этот промежуток приложение ещё не является полностью независимым от зарубежного сервиса.

### Этап C — полная независимость
- Перенести регистрацию/авторизацию, чаты, realtime и данные с Supabase на собственный backend и PostgreSQL.
- Удалить Firebase Cloud Messaging из обязательного пути. Отдельно решить, принимается ли RuStore Push как российский канал или ограничиваемся звонками при активном приложении/foreground service.
- Провести тесты двух устройств: Wi-Fi↔Wi-Fi, Wi-Fi↔мобильная сеть, мобильная сеть↔мобильная сеть, фоновый режим, восстановление после обрыва.

## Критерии приёмки

- В коде приложения и сервере нет Metered/Open Relay, Google STUN или Cloudflare STUN.
- Android получает только временные TURN credentials от собственного backend.
- Сигнализация и медиареле работают на узле, контролируемом владельцем проекта.
- Никаких платных SIP-аккаунтов и автоматически заканчивающихся пробных тарифов.
- Проверены два физических Android-устройства и сетевые сценарии выше.
- Документация честно обозначает ограничения: без круглосуточного доступного сервера нельзя гарантировать звонки между произвольными сетями.

## Важная текущая зависимость

В существующем приложении Supabase обслуживает учётные записи, сообщения, звонки и Realtime, а Firebase SDK присутствует для push. Поэтому замена одного TURN endpoint не делает весь ArturChat автономным. Полный отказ от зарубежных сервисов требует переноса и этих функций.
